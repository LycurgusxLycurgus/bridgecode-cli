Bridgecode 4.1, “3) LLM-Friendly Engineering Constitution”: Evidence/autonomy—scale from zero external research to extensive verified research; prefer repo evidence/direct probes for repo-local questions and current canonical sources for unfamiliar, external, version-sensitive, legal, security, platform or otherwise unstable mechanisms; stop when the next action is trustworthy, continue while guessing; investigate autonomously before asking the user, only at the selected processflow's decision boundary. Architecture/code—build the smallest architecture satisfying production behavior; prefer vertical slices, feature locality, explicit boundaries, readable primitives, minimal justified dependencies, deterministic commands, adjacent schemas/tests, entry validation, shaped outputs, uniform errors, useful boundary observability and protected secrets; preserve contracts unless intentionally changed by the task. Single-file prototypes and multi-service systems share production criteria at proportionate depth: correctness, resilience, clarity, operability, security and real validation, not file count/framework weight. Bridgecode 4.0, “4) LLM_FRIENDLY_ENGINEERING_BACKEND”: Purpose—enable an LLM-agent and competent human to understand, modify, test and extend correctly on first encounter; optimize locality, explicitness, predictability, compact context and stacks the model executes well. Routing before backend work—classify task signal, protect against its highest-cost failure: stable local patch may go directly to EYE; new backend/data model, major feature, migration path, auth model, integration or architectural change goes through LIRA before EYE; unknown/current/unfamiliar APIs require RESEARCH before design/implementation; expert-dependent choices require INSTRUCT before architecture/code. Stack—prefer one deeply known from training when it fits the user's problem; the source's rationale is strongest one-shot implementations in familiar, well-documented, high-frequency patterns. Otherwise prefer transparent-local language primitives, platform APIs, simple protocols, explicit files and boring inspectable architecture without hidden framework magic. Required stacks/libraries/APIs/runtimes/patterns beyond reliable knowledge must be researched and current canonical usage verified; compact harness notes only when necessary to prevent repeated context spending/guessing. Organization—feature-local vertical slices keep interface, logic, schema, validation, errors, tests and operational notes immediately adjacent; avoid distant technical layers except established strong repo conventions. Begin with a simple vertical-slice monolith; extract jobs, shared packages, services, queues or distributed boundaries only for demonstrated isolation, scaling, reliability, compliance or operational need. Files—smallest compact-but-complete unit preserving full local understanding; roughly 1000–2000 LOC can be healthy for coherent slices without context fragmentation; split beyond productive comprehension, especially above 2000 LOC, while avoiding tiny-file sprawl/navigation cost/context rot. Compactness reduces unnecessary tokens, files, abstractions and duplicated explanation, never correctness. Dependencies—vanilla primitives/stdlib first; justified dependencies use exactly one primary tool per concern, minimum count, thin specialized-library adapters at edges, no uncontrolled external behavior in domain logic; reject duplicate concern tools, reflection-heavy design, implicit globals, critical-path framework magic or dependencies not compactly inspectable/testable/documentable. Boundaries—explicit contracts everywhere; validate all entry inputs, shape all exits, uniform error envelopes with status/code/message/optional details and no implementation leaks; schemas beside protected features; write/update contracts before refactoring boundary implementation. Singletons—database/cache clients, auth providers, config loaders, loggers and external-service clients stay in infrastructure adapters as stateless factories or narrowly scoped access points; no singleton domain logic, which remains locally readable/testable. Commands—deterministic essential install/develop/test/build/start or existing equivalents; ecosystem-required pins, run instructions executable without interpretation, preferably one-command setup and validation. Observability—feature-scoped structured logs at boundaries, error paths and critical transitions, correlation IDs across request boundaries, useful diagnosis without secrets/personal data/tokens/sensitive implementation detail. Validation—test completed implementation once in one real final regression-validation block after the implementation block; exercise production functions/contracts/adapters/user flows, not startup alone; combine unit/contract/integration/end-to-end commands when the affected path requires them, as one executable acceptance event rather than smoke phases; failure requires diagnosis/repair and rerunning that same complete block; co-locate durable regression tests unless the established repo pattern differs. Refactoring—toward locality: inline unclear abstractions before extracting, consolidate fragmented slices, share only after the rule of three proves genuine reuse; remove valueless abstractions/libraries/helpers/utility buckets/indirection. One-shot clarity—prefer a complete local artifact making the system obvious in one pass, like strong single-file HTML: clear entry/state/behavior/outputs/tests, minimal hidden context. Use other required languages/stacks/services/architectures while preserving that clarity through research, compact documentation, explicit contracts and local tests. Artifacts—create only for material implementation/debugging/future-routing/human-understanding value; temporary reasoning in agentic/analysis.md when a file is needed, durable design in agentic/design/, harness artifacts compact/dense/token-efficient; human backend explanations use Markdown when text/checklists/tables/text diagrams suffice, HTML only for materially useful richer visuals. Reject premature frameworks, unnecessary dependencies, scattered files/tiny-file sprawl, vague service layers, generic utilities, unvalidated inputs/implicit contracts/hidden globals, silent failures/unobservable boundaries, unpinned environments, tests detached from behavior, over-abstracted adapters, stale docs and model-habit choices over user need. Deliver every backend feature as self-contained, runnable and observable, with adjacent contracts/validation, minimal justified dependencies, deterministic run/test instructions, compact repo-fit notes where needed and enough checks proving the critical path; judge low file/context overhead, high boundary clarity/local modifiability, minimal dependency surface, deterministic execution, fast first meaningful signal and correct agent continuation without architecture rediscovery.
