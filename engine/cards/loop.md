One loop builds what its one-block names. FOCUSED: tiny loops in the target stack and the architecture's layout, each the whole request when it is small, otherwise the next coherent part, judged by your own mini-review. FULL: the next-shot after a one-shot (or an exploration, or a failed pre-release gate), then small loops, each judged by an independent review.
1. PREVENT, the step back (tiny on FOCUSED, small on FULL): `{{cmd}} stepback tiny|small --targets <IDs> "<…>"`, routing the behaviour: LOCAL (one boundary, an exact failing input, an existing mechanism) → build directly; RELATIONAL (who owns what, what belongs to which run, what must happen together) → add a boundary model to the block: one row per boundary, the relation it requires, one discriminating check that keeps the valid form but swaps the owner or state, each row's check run on BEST; UNSETTLED (the mechanism is unknown) → no direct build: `{{cmd}} escalate FULL` on FOCUSED, the loop-breakers on FULL; UNDECIDABLE → a re-define (`{{cmd}} advance ASK --why "<…>"`).
2. PREVENT, the one-block: `{{cmd}} block "<…>"`: the next action written whole, in a familiar representation: the sketch of the code it writes, the criteria in scope, the route of the behaviour, the real inputs, the acceptance command. Files are split from it, never drafted separately.
3. Seen to fail on BEST: `{{cmd}} run --before -- <the target's check>` (the engine runs it in a worktree of BEST; `--judgment` when the evidence is the criterion's real output). The engine requires it for a target that already failed, and always when you judge.
4. Build the block on BEST, yourself or through the builders (dynamic and mechanical cards: `{{cmd}} call builder-dynamic|builder-mechanical`, append the block; merge their results by the merge card). A legitimate real input rejected, a protected test broken or a block assumption contradicted stops the build for a new step back.
5. Run the acceptance command, the affected tests (callers, command paths and shared fixtures of what changed) and the real path on HEAD: `{{cmd}} run -- <command>`; commit.
6. Judge (the engine says who): FOCUSED, `{{cmd}} judge loop --self <verdict file>`, your mini-review per criterion from the witnessed runs; FULL, `{{cmd}} call reviewer`, append the evidence and the test diff against BEST, then `{{cmd}} judge loop <ids>`. Settle every NOT_MET with `{{cmd}} reproduce`. The engine gives the outcome and the rung.
The next-shot is ONE loop, nothing else: one block that repairs every failing criterion (CORE and NON-CORE) and moves the whole one-shot into the architecture's layout (under Rosetta, into the target representation), judged on every criterion; criteria the one-shot established re-run with the same exit codes. Not PASS → the ladder; the next attempt is another next-shot. Never a chain of repair loops followed by a refactor loop.
Loops on disjoint files, data and criteria may run in parallel; only you merge.
